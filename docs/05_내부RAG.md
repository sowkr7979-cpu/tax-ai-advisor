# 章 05 — 내부 RAG (Internal Knowledge Pipeline)

> **이 章이 사용자 핵심 질문의 답**: "text split / embedding / Vector DB도 내가 직접 해야 하나?"
> → **그렇다. 단 '직접 통제'와 '직접 구현'을 구분한다.**
>
> | 항목 | 직접? |
> |---|---|
> | split 전략·임베딩 모델 선택·벡터DB 스키마/메타데이터·검색 전략·RAG 품질기준 | **직접 설계(통제)** |
> | 벡터DB *엔진* 자체 | ✕ 기존 라이브러리/DB 사용 |
>
> **연결**: ingestion 라이선스 게이트=`01_보안` · 메타데이터·시점=`02_출처` · 임베딩/검색 어댑터=`07_API`(src/ai) · 무근거 답변 차단=`08_환각방지` · 검색 품질 채점=`09`.

---

## 1. 왜 "한 줄 RAG"로는 안 되는가

기존 설계서의 "내부 지식 DB(RAG 30%)" 한 줄은 **실행 명세가 없다.** 세무 RAG는 일반 RAG와 다르다:

- **문서 구조가 제각각** → 하나의 splitter로 자르면 품질 붕괴(법령을 문단 길이로 자르면 조문 경계가 깨짐).
- **인용 가능성이 생명** → chunk마다 출처·조문번호·시점을 보존해야 답변이 근거를 가진다.
- **토큰 비용 이슈(신현우님 지적)** → 실무서를 통째로 넣지 않고 **관련 chunk만 회수**해야 한다.
- **기밀·격리** → 고객 자료와 공유 지식을 섞으면 안 된다(`01_보안`).

그래서 RAG는 **독립 파이프라인 10단계**로 설계한다(API 계층과 분리).

---

## 2. 파이프라인 개요 (10단계)

```
① 수집(Ingestion) → ② 분류(Classification) → ③ 구조인식 분할(Structure-aware Split)
→ ④ 메타데이터 추출 → ⑤ 임베딩 → ⑥ 벡터DB 적재/색인
→ ⑦ 하이브리드 검색 → ⑧ 재랭킹 → ⑨ 인용근거 답변 생성 → ⑩ 검색/감사 로깅
```
- **①~⑥ = 적재(오프라인)**, **⑦~⑩ = 질의(온라인)**.
- 코드 위치(Workpaper 2120): **오케스트레이션·분할·검색조립·로깅 = `src/`(deterministic)**, **임베딩·LLM·reranker 호출 = `src/ai/`(어댑터)**, **스키마 = `contract/`**, **벡터 데이터·로그 = 런타임(`runs/`)**.

---

## 3. ① 수집 (Ingestion)

- **소스(허용)**: 공개 법령/예규/판례(`L0`) · 라이선스 실무서·출판물(`L1`, "서점 제휴") · 합성 예시·내부 플레이북(`L2`) · 고객 자료(`L3`, 수임범위 내).
- **포맷**: PDF · **HWP/HWPX(한국 공문서 다수)** · DOCX · XLSX/CSV(TB·원장) · HTML. → 포맷별 파서. HWP·스캔 PDF는 OCR 경유(`07_API`).
- **라이선스 게이트(필수)**: `SourceLicense` 없는 `L3`/무권한 자료는 **적재 거부**(`SEC-004`). 전직장 데이터 차단.
- **표/숫자 자료**: TB·원장·재무제표는 자유텍스트 청킹이 아니라 **structured extraction**(행/열·계정과목·금액·기간) 우선 → 계산 Ground Truth(`src/`)로 연결.

## 4. ② 분류 (Classification)

적재 문서를 **문서유형**으로 라우팅(이후 splitter·메타데이터가 달라짐):
`법령` · `시행령/규칙` · `예규/질의회신` · `판례/심판례` · `내부 검토메모` · `실무서` · `회사 재무자료(TB/원장/FS)` · `계약서` · `증빙(세금계산서/통장)`.
- 자동 분류(규칙+모델) + 불확실 시 사용자 확인. `confidentiality_level`도 함께 추정(`01_보안`).

## 5. ③ 구조 인식 분할 (Structure-aware Split) — **핵심**

문서유형별로 splitter를 **다르게** 적용하고, **인용 메타데이터를 chunk에 박는다.**

| 문서유형 | 분할 기준 | chunk에 보존할 메타 |
|---|---|---|
| 법령 | **조 > 항 > 호 > 목** 단위 + **부칙·적용례·경과조치·별표·서식을 별도 locator로**(Codex·`RAG-015`) | 법령명·조문번호·**공포일·시행일(ProvisionVersion)**·부칙 적용근거 |
| 시행령/규칙 | 조문 + **위임관계(상위 법 조문)** | 위임 법조문·시행일 |
| 예규/질의회신 | **사실관계 · 질의 · 회신요지 · 관련법령 · 판단근거** 섹션. **단 실제 국세청 자료는 섹션명이 불규칙·복수질의 혼재** → **섹션명 정규화 + multi-issue 분할**(Codex·`RAG-016`) | 문서번호·issued_date·issuer·issue별 분리 |
| 판례/심판례 | **사건번호 · 쟁점 · 판단 · 결론** | court·decided_date·cited_provisions |
| 내부 검토메모 | **쟁점 · 검토의견 · 근거 · 결론** | 검토자·검토일·관련쟁점 |
| 실무서 | 장/절 + 의미 경계(semantic) | 출처·페이지·판수(edition) |
| 회사 재무자료 | row/column structured(청킹 아님) | 계정과목·거래처·금액·기간·증빙유형 |
| 계약서 | **조항(article)** 단위 | 조항번호·당사자·일자 |

- **chunk 크기·overlap**: 유형별 상이. 법령은 조문이 자연 경계(작은 조문은 병합, 긴 조문은 항 단위 분할 + 부모 조문 참조). 실무서는 토큰 기준(예: 512~1,024 토큰) + 10~15% overlap. **구조 경계를 토큰 길이보다 우선.**
- **parent-child(부모-자식)**: 작은 chunk로 검색하되 답변엔 **부모(조문 전체·예규 전체)** 를 함께 제공해 맥락 손실 방지.
- **citation-level chunk**: 인용 단위로 `source_locator`(조/항/호·page·paragraph)를 chunk에 고정.

## 6. ④ 메타데이터 추출

각 `Chunk`에 부착(= `02_출처`와 정합):
`doc_type` · `source_type` · `authority_rank` · `법령명/문서번호/사건번호` · `source_locator` · `effective_from/to`(시점) · `tax_type`(세목) · `귀속연도` · `client_id`(고객자료) · `confidentiality_level` · `license_id` · `content_hash`.
- **citation용 구조화 필드 분리(Codex·`RAG-017`)**: `source_locator`를 자유텍스트가 아니라 **조/항/호/목 구조 필드**로, 그리고 **공포일·시행일 분리 + 개정 이력 식별자(`amended_by`) + 부칙 적용근거**를 별도 필드로. → 인용 검증(`08 G2`)이 pinpoint·시점까지 기계 대조 가능.
- **이 메타데이터가 검색 필터·시점 유효성·인용·격리의 근거**가 된다.

## 7. ⑤ 임베딩 (Embedding)

- **모델 선택(직접 결정)**: **한국어·법률/세무 도메인에 강한 임베딩**. 임베딩 경로는 **단일 전송정책으로 일관화**(Codex — 05/07 불일치 제거):
  - `L3·L4`(고객 기밀): **기본 on-prem/사내 임베딩.** private endpoint(비학습·마스킹) 허용 여부는 **고객별 정책값(`API-013`)으로만** 결정·로깅. 정책 미허용 시 외부 전송 금지(`SEC-005`).
  - `L0~L2`(공개·라이선스): 외부 임베딩 API 허용(비학습, `SEC-008`).
  - **라이선스 자료(`L1`) 추가 검사(Codex·`API-014`)**: `SourceLicense`가 *적재*뿐 아니라 **embedding/파생색인/export/cache 허용권**까지 포함하는지 검사(계약상 외부 임베딩 금지 가능).
- **버전 관리**: `EmbeddingModel`(이름·차원·버전)을 기록. 모델 교체 시 **재임베딩 배치** + 인덱스 버전 분리(혼용 금지).
- **임베딩 입력**: chunk 본문 + 핵심 메타(법령명·조문번호)를 함께 임베딩해 검색 적중↑.

## 8. ⑥ 벡터DB 적재 · 색인

- **엔진**: 기존 벡터DB 사용(직접 구현 ✕). 추상화 어댑터(`src/ai/`) 뒤에 둬 **교체 가능**.
- **분리 색인(핵심 — "split embedding DB"의 실체)**:
  - **공유 참조 인덱스**(읽기전용): 법령·예규·판례·라이선스 실무서(`L0~L2`).
  - **테넌트 인덱스**(client별 파티션): 고객 자료(`L3·L4`). → 공유 인덱스와 **물리/논리 분리**(`SEC-003`).
- **하이브리드 색인**: dense(벡터) + **sparse(BM25/키워드)** 동시. 세무는 조문번호·세목·고유명사 정확매칭이 중요 → 키워드 인덱스 필수.

## 9. ⑦ 하이브리드 검색 (Retrieval)

1. **쿼리 계획(query decomposition)**: 복합 쟁점을 하위질의로 분해(예: "가지급금 인정이자 손금?" → ① 인정이자 계산 ② 손금불산입 요건 ③ 특수관계 판단).
2. **하이브리드**: dense + BM25 병합(예: RRF).
3. **메타데이터 필터(후보 *생성 전* 검색공간 제한 — Codex)**: `tenant_scope`(격리, 끌 수 없음·`SEC-002`)와 **시점(`effective_from ≤ 적용시점 < effective_to`)** 은 *재랭킹 전 필터*가 아니라 **검색 공간 자체를 제한**한다(애초에 후보에 안 들어옴). 그 위에 `tax_type` · `doc_type` · `authority_rank` 필터.
4. **parent-child 확장**: 적중 chunk의 부모(조문/예규 전체) 회수.
5. **top-k + context compression**: 관련 부분만 압축 회수 → **토큰 통제**(§12).

## 10. ⑧ 재랭킹 (Rerank)

- 1차 후보를 **reranker**(cross-encoder)로 정밀 재정렬. **후보 수 상한·latency SLA·한국어 세법 도메인 성능 기준**을 정의(Codex — `NFR-002`와 연동, 미정의 금지).
- 추가 재정렬 신호(소스 **내부** 스코어링 — 소스 간 가중혼합 아님): **본문 유사도 + 출처 신뢰도(authority_rank) + 문서유형 + 세목·귀속연도 일치 + 적용시점 유효성**.
- **"최신성"보다 "적용시점 유효성" 우선(Codex)**: 세무는 *가장 최신 법령*이 아니라 *그 사업연도에 유효한 버전*이 정답. 최신성 점수와 시점 유효성 점수를 **분리**(웹은 `WEB-012`).
- **시점 위배 후보 강등/배제**: 적용시점에 유효하지 않은 법령버전은 (검색공간에서 제외되며) 잔존 시 최하위.

## 11. ⑨ 인용근거 답변 생성 (Citation-grounded) — 내부RAG는 **②번 독립 SourceAnswer**

- 내부 RAG는 **②(INTERNAL_RAG) 채널만으로 완결된 답변(`SourceAnswer`)** 을 만든다(①법령MCP·③웹과 섞지 않음). 답변은 **회수된 근거 안에서만** 생성, 회수 밖 단정 금지(`08_환각방지`).
- 각 주장(`Claim`) → `Citation`(소스객체·pinpoint·applicable_basis) 부착(`02_출처`).
- **종합은 별도 단계**: ①②③ 세 `SourceAnswer`를 종합 에이전트가 claim 단위로 정합(`08 §5`, `03 ORCH-008~013`). 내부RAG는 종합 전 **자기 답변만 책임**.
- 근거 부족·충돌·시점 불명 → **단정 대신 회계사 검토항목**으로.

## 12. ⑩ 검색·감사 로깅 + 토큰 통제

- **`RetrievalRun` 로깅**: query·하위질의·필터·후보 chunk_id·rerank 점수·최종 채택·source_answer_id → **재현성**(`01_보안`·`SEC-007`).
- **토큰 통제 전략(신현우님 이슈 직접 대응)**:
  1. 통째 주입 ✕ → **top-k chunk만**.
  2. **context compression**(질의 관련 문장만 추출).
  3. **query decomposition**으로 하위질의별 소량 회수.
  4. parent 확장은 **필요 시에만**.
  5. 캐시(동일 쟁점·시점 재질의) — `07_API`.

## 13. RAG- 기능요구사항 (요약 — 전체는 `03_RFP`)

| FR-ID | 요구 | 수용기준(발췌) | 우선 |
|---|---|---|---|
| `RAG-001` | 문서유형별 split 전략 적용 | 법령/예규/판례/메모/회사자료 각 splitter 분기 | P0 |
| `RAG-002` | 법령=조/항/호/목 분할 + 조문번호·시행일 메타 보존 | chunk에서 조문번호·시행일 조회 가능 | P0 |
| `RAG-003` | 예규=사실관계·질의·회신요지·관련법령·판단근거 구분 저장 | 섹션 메타로 회신요지 단독 회수 | P0 |
| `RAG-004` | 검토메모=쟁점·결론·근거·검토자·검토일 메타 | 검토자/일자 필터 검색 | P1 |
| `RAG-005` | 검색 재정렬 = 유사도+출처신뢰도+문서유형+세목+귀속연도+**적용시점 유효성**(최신성은 별도 신호로 분리, `WEB-012`) | 시점 위배 법령버전 강등 | P0 |
| `RAG-006` | 답변은 chunk_id·source_id·조문/문단 위치 추적가능 | 임의 문장의 근거 chunk 역추적 | P0 |
| `RAG-007` | 공유 지식 인덱스와 테넌트 인덱스 분리 + 격리필터 강제 | 교차 회수 0건(`SEC-003`) | P0 |
| `RAG-008` | 하이브리드(dense+BM25) + 메타 필터(시점·세목·격리) | 조문번호 정확매칭 회수 | P0 |
| `RAG-009` | parent-child + context compression(토큰 통제) | 통주입 대비 토큰↓, 맥락 유지 | P1 |
| `RAG-010` | query decomposition(복합쟁점 분해) | 다쟁점 질의 하위질의 로깅 | P1 |
| `RAG-011` | 임베딩 모델 버전관리 + 교체 시 재임베딩·인덱스 분리 | 혼용 인덱스 0 | P1 |
| `RAG-012` | 회사 재무자료 structured extraction(청킹 아님) | TB/원장 행·계정 추출 | P1 |
| `RAG-013` | `RetrievalRun` 로깅(재현성) | 답변→회수근거 복원 | P0 |
| `RAG-014` | 근거 부족·충돌·시점불명 시 단정 금지(+**코퍼스 부재 정직표기**) | abstain·검토항목 전환(`08`); **내부 RAG 코퍼스가 비어 있으면 회수 합성 0 + 채널 ②를 `SILENT(커버리지 갭)` 으로 검토패키지에 정직 표기**(`OUT-007`, 변경②) | P0 |

## 14. 면접 한 줄

> "RAG를 '문서 잘라 벡터DB에 넣기'로 보면 세무에선 실패합니다. 법령은 조문 단위, 예규는 회신요지 단위로 **다르게 잘라야** 하고, chunk마다 **조문번호·시행일**을 박아야 인용이 살아납니다. 저는 *split 전략·임베딩 선택·검색 설계*는 직접 통제하고, 벡터DB 엔진만 기성품을 씁니다. 그리고 실무서를 통째로 안 넣고 **관련 chunk만** 회수해 토큰 비용을 잡습니다."
